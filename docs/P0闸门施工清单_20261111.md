## 0. 先读：三处与体检报告不一致的实测结论

这三条会**改变**施工方式，照原报告写会做错：

### 0.1 G-03 的落点不是 `app/app.py` 的路由，而是 `app/routes/purchase_order.py`

- 体检报告写的 `app/app.py:11839-11915` 是**共享核心** `_create_in_order_from_purchase_order_core(order, warehouse='', remark='', submitted_qty_by_id=None)`；

### 0.2 G-01 的接口前端**零调用**

全仓 grep（`app/templates`、`app/static`、`app/android-native-wms`）对 `/in_order/<id>/update_completed` 命中为空，只有测试在调。工程上的含义：

- 补审计不会打断任何现有 Web/App 操作；
- 「直接封掉改数通道」也不会打断界面，但**会打断任何外部脚本/手工 API**。封通道属于**削减既有能力**，须用户逐项授权，不作为本批默认动作。

### 0.3 G-06 不能"挂个调度去跑 `scripts/verify_inventory_identity.py`"

该脚本 `main()` 第一行就是 `_require_owned_test_profile()`（`scripts/verify_inventory_identity.py:538-539` → `verify_db_guard.py:7-15`），在普通 Windows 生产进程下**必 `SystemExit`**。它设计上只能跑在 LPAC 合成测试身份里。所以"生产每日巡检"必须另写**生产可用**的巡检实现，不能复用这个脚本入口。

同时：`find_location_ledger_mismatches()`（`app/services/warehouse_stock_service.py:93-159`）虽然生产可用，但**只覆盖 ①≠Σ② 与仓级 ②≠③，不含 ①≠Σ③**——而 ①≠Σ③ 才是库存烂账的主信号。

### 0.4 附加：G10 有一条 AGENTS 硬约束挡在前面

`AGENTS.md` §一 铁律：

> 系统不得为任何账号（包括 bootstrap admin）自动生成随机密码。当 `WMS_BOOTSTRAP_PASSWORD` 未设置时，系统必须使用固定默认密码（'admin'）并给出警告，而非 `secrets.token_urlsafe` 等随机生成器。

**关键坑**：`log_audit` 自己 `db.session.commit()`。而本函数的业务提交在 `in_order.py:2488`。若在**业务提交之前**调 `log_audit`，会把半成品状态提前落库；若中途失败回滚，审计却已提交（谎报成功）。**必须先业务 commit，再写审计**（与 delete/revert 的写法一致，它们都是先 `db.session.commit()` 再 `log_audit`）。

### 2.2 改法（主线：补审计 + 原因必填，不动能力）

**改动 1：函数内导入补两个符号**

`in_order.py:2209-2217` 的 `from app import (...)` 追加 `log_audit, log_operation`。

**改动 2：入口收集"变更摘要"，业务提交后一次写入**

在 `2484`（`recalculate_order_total(order)`）之前，按三路分支累积 `audit_old` / `audit_new`（结构建议）：

```python
audit_old = {'order_no': order.order_no, 'items': {str(it.id): float(it.quantity or 0) for it in order.items}}
# 三路分支内各自追加：
#   删行  → audit_new.setdefault('removed', []).append({'item_id': item.id, 'quantity': q})
#   增行  → audit_new.setdefault('added', []).append({'item_id': new_item.id, 'quantity': q})
#   改量  → audit_new.setdefault('changed', []).append({'item_id': item.id, 'from': old, 'to': new})
```

注意 `audit_old` 必须在**任何修改之前**快照（`order.items` 一旦 `db.session.delete` 就少一行）。

**改动 3：`in_order.py:2488` 的 `db.session.commit()` 之后追加**

```python
db.session.commit()
log_operation('修改已完成入库单', f'入库单：{order.order_no}', 'in_order', id)
log_audit(
    'update_completed_in_order', 'in_order', id,
    target_name=order.order_no,
    old_data=audit_old,
    new_data=audit_new,
    reason=(request.get_json(silent=True) or {}).get('reason') or None,
)
```

**改动 4：原因必填**

在入参校验处（`2225-2243` 附近的 payload 解析）加：本次**存在数量类变更**时 `reason` 必填且 `len(strip()) >= 2`，否则 `return fail('修改已完成入库单的数量必须填写原因')`。纯表头备注类变更不强制。

> `reason` 列是 `String(200)`，务必 `[:200]` 截断。`audit_new` 里 `items` 全量快照可能超长——`old_data/new_data` 是 `Text`，无长度限制，但建议只存**差异**（上面结构即是差异），不要存全量明细，避免审计表膨胀。

**改动 5：前端（可选，非必需）**

`in_order_detail.html` 无该入口，本批不必改前端。若后续要开入口，必须同时加"原因"输入框。

### 2.3 备选方案（需用户授权，不作为本批默认）

直接封通道：函数首行 `return fail('已完成入库单不允许直接改数量，请先反提交后再修改')`，函数体保留不删（便于将来恢复）。收益是彻底消灭"改数不留痕"；代价是失去"完成态微调"。**必须用户明确同意后才做**，且要确认无外部脚本依赖。

### 3.2 改法

**改动 1：头级保留来源**

`out_order.py:232` → `source_sales_order_id=source.source_sales_order_id,`
同步删掉 `220-221` 的剥离提示，改成：

```python

```

**改动 2：行级保留来源**

`out_order.py:253` → `source_sales_order_item_id=item.source_sales_order_item_id,`

**改动 3：加写锁与审计（与 delete/revert 对齐）**

当前 copy 无锁、无审计。补：进入 `try` 前 `_acquire_order_write_lock(OutOrder, id, ('pending','completed'))` 防止复制到一半源单被删；成功后 `log_audit('copy_out_order', 'out_order', new_order.id, target_name=new_order.order_no, old_data={'source_order_no': source.order_no})`。

**改动 4：明确"确需无来源"的出口（关键，别省）**

保留来源后，业务上仍存在"拿这张单改改发给另一个客户"的合理场景。必须给显式出口，否则用户会绕过系统（手工改库或删来源）：

- 方案（最小改动）：copy 请求体支持 `strip_source: true`；为真时**同时**把 `business_type` 强制改为 `'其他出库'`（`out_order.py` 里 `business_type` 已按 `prefix` 推导，需显式覆盖），并在 remark 写明"无来源出库（原单 SO…）"。
- 这样"销售出库"类型**永远**有来源，"其他出库"类型**永远**无来源，`sales_outbound_remaining_check` 的不变式变成"凡销售出库必有来源"。

**改动 5：完成闸门补一条不变式（防回归）**

在 `out_order.py:1208` 的 `if order.business_type == '销售出库':` 分支内，先断言"所有行都有 `source_sales_order_item_id`"，缺则报错：

```python

if missing:
    db.session.rollback()
    return api_error('销售出库明细必须关联销售订单行，请重新从销售订单下推')
```

这条是**纵深防御**：即使将来又有别的入口造出无来源销售出库，也会在完成时被挡住，而不是静默超发。

### 4.2 改法（四层，缺一层都留着洞）

**第 1 层：核心加锁（覆盖三条调用方）**

在 `_create_in_order_from_purchase_order_core` 开头，`_acquire_order_write_lock(PurchaseOrder, order.id, ('pending','partial','closed'))` 取代调用方传入的已读实例。注意：路由层已经 `get_or_404` 读过一次，核心内需要按 id 重新加锁读。

`expected_status` 用 `('pending','partial','closed')` 而不是单一值——采购单允许"已关闭但补收"是现状行为，收窄会打断业务。**不要**把 `completed` 放进来（已收满不该再推）。

**第 2 层：复用已有 pending 草稿（与销售同构）**

核心内、锁之后、建单之前：

```python

    source_purchase_order_id=order.id, status='pending'

if existing:

```

返回二元组语义从 `(in_order, error)` 扩展为 `(in_order, None|'existing'|error_msg)`。**所有调用方必须改**：`purchase_order.py:947`、选单 `:829`、`app.py:18058`、`app.py:18150`。漏改一处会把 `'existing'` 当错误串返回给用户（显示成"existing"这种乱码 msg）。

**第 3 层：写 `DocumentPushLine` 留痕**

```python

    source_document_type='purchase_order', source_document_id=order.id,
```

`request_id` 由路由从 payload 取；缺省时用 `uuid4()`（但那样就失去幂等，前端必须传）。**注意** `_source_has_active_push()` 只查 `source_document_type in ('purchase_in_order','other_in_order','product_in_order')`（`app.py:26605-26608`），新类型 `purchase_order` **不会**误触发入库单的下推保护，安全。

**优先级**：P0-6｜**批次**：一-C｜**风险**：低（默认行为不变）

### 7.1 现状（已核实，两处与报告不同）

| 事实 | 位置 |
|---|---|
| 默认密码回退 `os.environ.get('WMS_BOOTSTRAP_PASSWORD') or 'admin'`，**出现 2 次** | `app/app.py:7097`、`:7154` |
| 未设置时 `app.logger.warning(...)`，**不阻断启动** | 同上 |
| `must_change_password = not bool(env)`（默认弱密码强制改密） | `app.py:7110-7112`、`:7175` |
| 强制改密拦截（页面 302 / API 403） | `app.py:4806-4825` |
| **自动解锁**：`if user.status == 'disabled': user.status = 'normal'` | `app.py:7142-7151` |
| 只匹配 `'disabled'`，**不匹配 `'inactive'`**（两者 `is_active` 都为 False） | `app.py:8362-8367`、`models/core.py:53` |
| **`ensure_*` 只在 `initialize_database()` 内被调用** | `app.py:7229-7230` |
| `initialize_database()` 在 `WMS_NO_DB_TOUCH=1` 时**早退**（不执行 bootstrap、不解锁） | `app.py:7218-7232`、`:229-243` |
| 生产入口 `run_wms_task.bat:14` / `start_wms_offline.bat:14` 均设 `WMS_NO_DB_TOUCH=1` | — |
| 停用保护：不能禁用自己；至少保留一个启用管理员 | `routes/user_auth.py:702-714`、`app.py:8376-8381` |
| 部署清单**无初始口令检查项** | `PRODUCTION_DEPLOYMENT_CHECKLIST.md:22-30` |
| 静态回归锁定该字面量 | `scripts/verify_wms_bugs.py:464-472`（BUG-NEW-005） |
| 安装脚本文案测试 | `tests/test_install_scripts_golden.py:198-215` |

**重要推论**：在现役托管入口（`WMS_NO_DB_TOUCH=1`）下，「启动期自动解锁」**根本不执行**。它是"首次部署/手工初始化"路径（`tools/init_portable_database.py` 设 `WMS_NO_DB_TOUCH=0`）的行为。这降低了风险等级，但也说明"改这段代码"对现网无即时影响。

### 7.2 改法（三项，均不改变默认行为）

**改动 1：自动解锁加显式开关（默认保持现状）**

`app.py:7142-7151` 改为：

```python
if user.status == 'disabled' and _env_flag('WMS_AUTO_UNLOCK_DISABLED_ADMIN'):
    ... 原解锁逻辑 ...
    app.logger.warning("Admin account auto-unlocked by WMS_AUTO_UNLOCK_DISABLED_ADMIN=1 (was disabled)")
```

默认 **0 = 不解锁**？还是 **1 = 解锁（保持现状）**？

必须选后者才符合 R8「不引入行为变更」——但那样缺陷仍在，只是变成"可选关闭"，等于没修。

**建议**：默认改为**不解锁**（即 `_env_flag` 缺省 False），并在部署清单写明"若运维误禁 admin，设置 `WMS_AUTO_UNLOCK_DISABLED_ADMIN=1` 后重启一次，解锁后立即改回 0"。理由：
- 现网入口下这段代码本就不执行，改默认**不产生现网行为变化**；
- 首次部署路径下，"静默解锁"违背"停用即停用"，且 `_has_other_active_admin` 已保证不会全锁死；
- 恢复通道明确、可审计（有 warning 日志）。

**此默认值变更需用户确认后再动手**，清单默认按"改为不解锁"写。

**改动 2：部署清单加硬项（文档，零风险）**

`PRODUCTION_DEPLOYMENT_CHECKLIST.md` §3 配置检查加：

```
- [ ] 已设置 WMS_BOOTSTRAP_PASSWORD（非 admin）；未设置时启动日志会告警，且首次登录强制改密
- [ ] 已确认 WMS_AUTO_UNLOCK_DISABLED_ADMIN 未设置或为 0
```

同步 `上线部署说明.md`、`说明.txt`（如需）。三处文案必须一致，`tests/test_install_scripts_golden.py` 有相关断言。

**改动 3：启动自检加一行显式风险提示（不阻断）**

`app/startup_check.py` 的 `log_startup_self_check` 增补：当 `WMS_BOOTSTRAP_PASSWORD` 未设置**且**库内存在 `must_change_password=True` 的账号时，banner 增加一行 `config-check: WARN 初始口令未设置（默认 admin 生效中）`。**只告警，绝不 raise**（有 `validate_production_security_config` 与 `SECURE_KEY` 两个"拒绝启动"先例，但这里不能用——见 §0.4）。

**必须保留的字面量**：`app.py` 内 `"os.environ.get('WMS_BOOTSTRAP_PASSWORD') or 'admin'"` 原样存在，否则 `scripts/verify_wms_bugs.py:464` 会红。
