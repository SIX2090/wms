# Windows 自动服务启动与部署（A09，2026-10-17）

本说明对应 `app/start_wms_auto.bat`、`app/service_launcher.py` 和 `deploy_cloud.bat`。当前修复分两部分：启动配置与新服务部署保护，以及随后验证的 NSSM 托管维护边界。不要把普通进程更新器直接用于受服务管理器托管的实例。

## 启动模式

- **HTTPS**：设置 `WMS_DEPLOYMENT_MODE=https`，未设置 Secure Cookie 时启动器补为 `SESSION_COOKIE_SECURE=true`。配置 Nginx HTTPS 反向代理到本机 WMS，再经 HTTPS 登录；本机 HTTP 登录页的健康检查不等于 HTTP 登录模式。
- **可信 HTTP**：只有在明确接受可信本机/内网 HTTP 场景时，设置 `WMS_DEPLOYMENT_MODE=trusted-http`。启动器仅在没有显式禁止值时设置 `WMS_ALLOW_INSECURE_COOKIE=1`。

没有模式时，只有已经明确设置 Secure Cookie 或 HTTP 放行才能推导模式；其他情况拒绝启动。互相矛盾的模式、显式禁止值、非法端口均返回非零，不会通过覆盖禁止值来让检查通过。其他配置保留，包括 `SECRET_KEY`、显式 `WMS_ALLOW_AUTO_SECRET_KEY=0`、数据库路径及端口。

自动 BAT 入口先调用 `service_launcher.py --batch-config` 检查配置与已有业务库，成功后直接执行本目录绝对路径 `run_server.py`。跨 BAT 边界只传固定模式、Cookie 标志和已验证端口，不生成或执行环境脚本；预检失败不启动服务。

自动服务入口关闭启动时拉取代码，避免监督进程运行期间修改代码。维护更新需要统一管理服务的停止、备份、代码与依赖、恢复及检查。

## 新服务部署

`deploy_cloud.bat` 默认选择 HTTPS。它用于**新建服务**：

1. 已有同名 Windows 服务、端口被占用，或无法完成检查时，拒绝部署，不停止或删除已有服务。
2. Python 安装完成后，使用同一解释器检查生产配置、空闲端口及已初始化的 SQLite 业务库。缺库或校验失败时不注册服务，不自动初始化账号或重置数据库。
3. 首次安装应先通过离线安装流程完成初始化，或迁入经验证的业务库；检查命令不会完成该步骤。
4. 配置 NSSM 时保存部署模式并关闭启动拉取；每项设置失败均中止。失败现场可能包含部分注册的新服务，需要核对状态、日志后人工处理，不能称为“完整回滚”。
5. 只有本安装目录的 `run_server.py` 监听进程身份及登录页均通过检查，才报告部署成功。其他程序返回 HTTP 200 不算成功。

`--check` 只验证配置；`--check-idle --check-database` 额外检查端口和业务库；`--health` 检查运行进程与登录页。它们不会初始化数据库、创建账号或修改密码。

服务账户所需的密钥、数据库路径和其他环境配置必须配置在该账户/服务中，不能把交互终端中临时 `set` 的值当成已经持久化。NSSM 的 `AppEnvironmentExtra` 是整组替换，增加配置时应保留原有条目；不要反复运行部署脚本来重建既有服务。

当前不通过真实生产部署验证脚本，也不以模拟服务测试代替生产启用确认。已有生产重启的审批拦截记录保持，不绕过执行。
