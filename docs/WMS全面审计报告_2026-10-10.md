### 1.1 实测结论：当前账是可信的

只读校验 `app/instance/inventory.db`：

| 判据 | 实测值 | 结论 |
|---|---|---|
| ① 总账 `material.stock` 合计 | **35,186.87** | — |
| ③ 流水 `stock_transaction` 合计（3386 条） | **35,186.87** | ✅ **完全相等** |
| ①≠③ 的物料数（容差 0.01） | **0 / 1245** | ✅ 逐物料零差异 |
| 逐仓加总 | wh1 1356.2 + wh2 33357.67 + wh4 473.0 = 35186.87 | ✅ 无串仓漏计 |
| 负库存物料 | **0** | ✅ |
| 悬挂流水（指向已删单据） | **0 / 0 / 0** | ✅ |
| `warehouse_id IS NULL` 流水 | **0 条** | ✅ |
| ② 库位账 `location_inventory` 行数 | **2 行** | 🔴 见 1.4 |

**37 个库存写入点已穷举**，每个"正向"都有严格对称的"回退"（`in_order.py:1930↔2467`、`out_order.py:1182↔1231`、`adjustment.py:459/472↔522/535`、`transfer.py:527↔592` 等全部核对通过）。

### 1.2 🔴 高危：仓库级扣减不是原子的（TOCTOU）

```
app/app.py:4774   available = get_warehouse_stock_quantities(warehouse_obj).get(...)   # 读
app/app.py:4790   sa_update(Material).where(condition).values(...)                      # 条件 UPDATE 只看【全局】Material.stock
```

**并发场景**：手机扫码 / Android `/api/outbound` 路径（`mobile.py:505-581`、`native_api.py:1194-1226`）**完全没有 `_acquire_order_write_lock`**，而单据级锁只保护"同一张已存在单据"的操作。

两个请求同时建单出库同仓同物料 → 各自读到仓库可用 10 → 条件 UPDATE 只看全局 `stock>=10` → **两次都成功** → 该仓账面变 −10，而①仍为正，**无报错**。

> 修复：把仓库级校验下推为同一条 SQL（`stock_transaction` 按 `(material_id, warehouse_id)` 做 `HAVING SUM(quantity) >= :qty`），或给移动端路径补物料级串行化；同时显式捕获 `OperationalError` 返回 409 而非 500。

### 1.3 🔴 高危：一旦有人在系统设置里打开"库位管理"，立即生产事故

实测 `location_inventory` 全表只有 2 行，且**都是脏数据**：

| material | code | 仓 | location | 库位账 | 该仓流水③ | ①总账 |
|---|---|---|---|---|---|---|
| 727 | 207005 | 2 库存仓 | WH002 | **1.0** | 0.4 | 0.4 |
| 615 | 101001 | 1 项目仓 | WH001 | **5.0** | 0.0 | 0.0 |

开启后：`get_warehouse_stock_quantities` 切到读库位账 → 物料 101001 凭空多 5.0；**其余 1243 个物料库位账恒为 0** → 库存查询/报表/手机端全部显示 0 → **所有出库被拒**；存量单据无库位 → 调整单/调拨完成全面失败。

> 修复：① 在开关页加前置校验——开启前先跑库存恒等式，有差异则拒绝开启；② 写一个按流水 `(material_id, warehouse_id)` 净额回填 `location_inventory` 的一次性工具（**当前 `scripts/` 下不存在**）；③ 先清理这 2 行脏数据。

### 3.2 🔴 迁移机制处于危险状态


> **后果：谁现在跑 `flask db upgrade`，会立刻撞 `duplicate column name: location` 失败。**
> 当前是"两头都有、两头都不准"的最危险状态。必须二选一：`alembic stamp head` 对齐后禁止裸 ALTER，或彻底废弃 Alembic。

### 3.3 🔴 12 个外键列在库中无约束

模型声明 163 个 FK，库中实际 159 个。缺失的 12 列（涉及 `opening_stock_doc`、`opening_stock`、`stock_transaction.warehouse_id`、`in_order.source_sales_order_id`、`employee.department_id` 等）。

所有 159 条现存 FK 的 `ON DELETE` **全部是 `NO ACTION`**，零级联。

## 四、前端与接口

### 4.1 🔴 确定性 404

`app/templates/base.html:3347,3353` 调用 `/draft/<id>` 和 `/draft/<id>/edit`，**后端全仓无此路由**。AI 单据草稿确认卡的「编辑」「确认创建」两个按钮点了必然 404。

### 4.2 🔴 106 处 Promise 链 `fetch` 无 `.catch`

模板中含 `.then()` 但无 `.catch()` 的 fetch 共 **106 处**。典型 `after_sale_out.html:203-214`：

```js
fetch(`/after_sale_out/${id}/complete`, {method:'POST', ...})
  .then(res => res.json())
  .then(data => { ... });      // ← 无 .catch
```

**500 时**：`res.json()` 对 HTML 响应抛 `SyntaxError` → 无 catch 承接 → **页面零提示，确认框已关闭，用户以为操作成功**。

> 一处改动全站生效：在 `base.html:71-87` 的 fetch 猴补丁里加全局兜底，或挂 `window.addEventListener('unhandledrejection', ...)`。

### 4.3 🔴 手机网页端绕过"采购入库必须关联采购订单"

PC 端（`in_order.py:1270/1400/1473/1617`）与 Android（`native_api.py:931/3475`）**都强制**，唯独手机网页端 `mobile.py:463` / `:856` **硬编码 `business_type='产品入库'`** → 手机端扫码入库永远生成"产品入库"，**永远不会生成"采购入库"**，报表按"采购入库"归集时手机端数据永久缺失。

另有：Android 出库有独立预检端点 `/api/outbound/preflight`，手机端 `scan_submit` mode=`out` **无预检**直接扣减。

2549+ 行，依赖 Print Spooler / Chrome或Edge / PowerShell / WScript.Network COM。
