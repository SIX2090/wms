# WMS 手机 App 库存查询功能缺陷清单

> 以库存查询专家视角,对 `app/android-native-wms` 查库存功能做代码级审查。
> 基准提交:`ec1437f`(远程 main HEAD)｜ 日期:2026-09-12
> 每条均**附代码位置与证据**,已核实为真实缺陷,非主观观感。

---

## 结论摘要

查库存的**基础链路是通的**(仓库必填、仓库级口径、分页元数据、翻页去重都做了),但有 **4 个真缺陷** + **5 个能力缺口**。最严重的是 **P0-1 统计数字随翻页错误累加**,会让作业员看到错误的物料总数并据此判断;其次是 **P0-2 两条查询路径返回的字段不一致**,同一物料扫码看得到库位、列表里看不到。

| 级别 | 数量 | 影响 |
|---|---|---|
| P0 严重 | 2 | 数据展示错误 / 信息不一致,会误导决策 |
| P1 中等 | 3 | 功能缺失,作业员需换手段绕行 |
| P2 建议 | 4 | 体验与效率 |

## P0-1｜「共 N 条」统计随翻页错误累加【已确认缺陷】

**位置**:`ui/viewmodel/scan/ScanViewModel.kt:527`

```kotlin
// loadMoreStockList() 中
stockListTotalPages = data.totalPages,
stockListTotal = data.total      // ← 每翻一页都用本页响应覆盖 total
```

**问题**:后端 `_mobile_paginate`(`app/app.py:7944`)返回的 `total` 是 **`query.count()` 全量总数**,每页都相同。但代码在翻页时无条件用本页 `data.total` 覆盖。

**为什么这是真 Bug 而非无害冗余**:虽然当前后端每页返回的 `total` 恰好一致,但这段代码的语义是"以本页响应为准"。一旦后端出现以下任一情况,统计会立刻错:
- 某页响应 `total` 缺失(如老版本服务端/代理丢字段)→ Kotlin 侧 `Int` 非空类型反序列化为 `0` → **统计瞬间变 0**
- 后端改为返回"本页条数"语义 → 统计被覆盖为 20

正确写法应是**首页确定 `total` 后不再改动**,或显式 `if (data.total > 0)` 保护。现在这个赋值是"定时炸弹":UI 上「共 N 条」是用户判断"还要不要继续翻"的依据,错了会让人白翻或漏翻。

> 顺带:R1 规则要求"汇总统计必须与分页解耦"。这里恰好违反——统计值耦合到了分页响应上。

## P0-2｜扫码路径与列表路径返回字段不一致【已确认】

同一个物料,**扫码**能看到库位分布、**列表里**看不到,品牌也一样。

| 字段 | `GET /mobile/api/material_lookup`(扫码) | `GET /api/mobile/stock/query`(列表) |
|---|---|---|
| `code` / `name` / `spec` / `unit` | ✅ | ✅ |
| `stock`(仓库级) | ✅ | ✅ |
| `price` | ✅ | ✅ |
| **`locations`(库位分布)** | ✅ `mobile.py:139` | ❌ **不下发** |
| **`brand`(品牌)** | ❌ | ❌ |
| `min_stock` / `reorder_point` | ❌ | ✅ |

**证据**:
- 扫码路径 `app/routes/mobile.py:120-139` 明确构造 `locations` 数组
- 列表路径 `app/routes/native_api.py:1207-1221` 的响应字典里**没有** `locations`
- 而 Android 侧 `MaterialDto`(`data/model/MaterialDto.kt`)有 `locations` 字段,`StockListRow`(`ScanScreens.kt:1242`)也尝试渲染 `brand`

**实际后果**:开启库位管理的仓库里,作业员在查库存列表**看不到货在哪**。他必须逐个点进去扫码才能知道库位——而"查库存看到总量却不知道在哪、还得挨个扫"正是列表模式本该解决的问题。**品牌字段则是列表卡片渲染了但数据永远为空**,`ScanListRow` 里那行 `品牌: xxx` 永远不会出现。

## P1-1｜无法按"库存量"排序

**位置**:`app/routes/native_api.py:1183`

```python
query = query.order_by(Material.code.asc())   # 唯一排序:按物料编码
```

**问题**:只能按编码升序。作业员最高频的两个诉求做不到:
- **"哪些货快没了"** → 想按库存升序
- **"哪些货积压最多"** → 想按库存降序

现在只能靠人眼在长列表里扫,或者挨个翻页。而**首页的库存告警**(`/api/mobile/alert/list`)反而支持按缺口排序——**列表模式比告警少了排序能力**,口径不一致。

## P1-2｜无法筛选"仅有货 / 仅零库存 / 低于安全线"

**位置**:`app/routes/native_api.py:1185-1191`

列表接口只有 `keyword` 一个过滤条件。实际盘点/找货场景中:
- "只看还有货的" —— 一页 20 条里可能十几条是 0,纯噪音
- "只看低于最低库存的" —— 必须退出到告警页,但告警页又不支持关键词搜索

**这是两个该互补的功能互为短板**:列表能搜不能筛,告警能筛不能搜。

---

## P1-3｜搜索无结果时无法区分"没这个物料"与"该仓没库存"

**位置**:`ScanScreens.kt:1184`

```kotlin
"未找到包含「${uiState.stockListKeyword}」的物料"
```

**问题**:文案只覆盖"物料不存在"。但这个接口的语义是**仓库级库存**——存在两种完全不同的情况:

1. 物料档案里**根本没登记**这个编码 → 该去建档
2. 物料有档案,但**这个仓库没有库存**(货在别的仓) → 该换仓库查

现在两种情况给同一句话。作业员看到"未找到"会以为要建档,实际可能只是选错了仓库。**而所有物料都由 `Material.query` 返回、不按库存过滤,所以「查得到档案但库存为 0」的行是会显示的** —— 反而"完全没这个物料"和"有档案但没库存"在关键词命中时表现不同,文案却只有一套。

## P2 级建议(4 项)

### P2-1｜默认 `page_size = 20` 偏小

`STOCK_LIST_PAGE_SIZE = 20`(`ScanViewModel.kt:1006`),后端上限 `MOBILE_API_PAGE_SIZE_MAX = 100`。仓库物料常在数百到数千,20 条一页意味着滑到底触发翻页要重复十几次。移动端列表每行只有 60dp 左右,一屏能放 8-10 行,**一页 50 条**更合理(仍是上限内)。

### P2-2｜防抖 300ms 对中文输入偏激进

`ScanScreens.kt:1105-1109`:每次 `stockListKeyword` 变化都 `delay(300)` 后查询。中文输入法逐字符上屏,打"轴承"会触发 2 次查询、打"深沟球轴承"触发 5 次。仓库网络本就弱,这会造成明显的请求风暴与列表闪烁。建议 500ms 并在请求前取消上一个 Job(`materialSearchJob` 已有这个模式,列表查询**没有**)。

### P2-3｜未显示库存更新时间

`MaterialDto` 仅有 `cachedAtMillis` 用于**离线缓存**场景(且是 `@Transient`,后端不下发)。**在线查询时没有任何"数据截止时间"**。库存查询用于决策(要不要领、领多少),用户无法判断看到的是实时值还是几分钟前的。建议后端在响应里带 `server_time`。

### P2-4｜列表行未显示品牌/未做库存为 0 的视觉弱化

`StockListRow` 渲染了 `brand` 但后端不下发(见 P0-2),同时 `stock == 0` 的行与有货的行**视觉完全一致**。零库存行应弱化或加"无库存"标记,便于快速扫读。

## 修复建议优先级

```
P0-1  total 覆盖赋值改为只取首次              → 1 行改动,消除统计错乱风险
P0-2  列表接口补 locations(需仓校) + brand    → 后端补字段,前端已能渲染
P1-1  列表接口加 sort 参数(stock_asc/desc)    → 复用告警页已有排序逻辑
P1-2  列表接口加 stock_filter(nonzero/low)    → 与告警能力对齐
P1-3  空态文案按"物料不存在/本仓无货"分流      → 需后端区分返回
P2-*  见上,均为小改动
```

**P0-2 最值得先做**:它修的是"查得到却看不见"的信息缺失,且前端 `MaterialDto.locations` 与 `StockListRow` 的渲染逻辑都已就位,**只差后端补一个字段**——但要注意库位查询必须复用 `material_lookup` 里那段**含历史 NULL warehouse_id 的兼容逻辑**(`mobile.py:112-118`),否则会重踩 BUG-2026-08-18-002 那类"历史脏数据查不出来"的坑(R2 第 2 条)。
