# WMS 手机 App 智能化路线图

> 基于对 `SIX2090/wms` 仓库（浅克隆 HEAD `1692882`，1330 文件）的真实代码调研产出。
> 结论先行：**这个 App 的 AI 底座已经相当完整，真正的缺口不在"再加模型"，而在"把已有智能送到作业员手边 + 让 App 在弱网/无网下不瘫痪"。**
> 编制日期：2026-09-12 ｜ 遵循 `AGENTS.md` 业务铁律（AI 只出草稿，人工提交/审核/完成）、R5（低置信度回退人工）、R2（多仓库边界必验）

---

## 一、现状盘点：已经有的智能（不要重复开发）

调研 `app/android-native-wms`（68 个 Kotlin 源文件）与后端 `app/ai/`（5 个子模块）后，确认 App 已具备以下能力。**这些都属于台账"已完成能力基线"，禁止当作新功能重做。**

| 能力域 | App 已有实现 | 后端支撑 | 台账编号 |
|---|---|---|---|
| **单据识别** | `AiScreens.DocumentOcrScreen` 拍照 → OCR → 确认 → 生成入库草稿 | `/api/ai/document_ocr` + `documents/extractor.py` | AI-MOB-OCR-F01/F02 |
| **识物** | `ObjectRecognizeScreen` 拍照识外包装文字/图形外观 | `/mobile/api/recognize_material` | AI-MOB-REC-F01 |
| **识物盘点** | `StocktakeRecognizeScreen` 拍照加入盘点清单 | 同上 + 盘点流 | AI-MOB-REC-F02 |
| **语音指令** | `VoiceCommandViewModel` 三层引擎（腾讯云 ASR → sherpa 本地 → 系统识别）+ 22 条领域同音纠错表 | `/mobile/api/asr` + `app/tencent_asr.py` | AI-MOB-VOICE-F01 |
| **语音建单** | 说「领8*25螺丝 1000个」→ 两阶段编排（dry_run 解析 → 消歧 → 确认 → 建草稿） | `/api/mobile/voice_out_draft` 六层降级匹配 | AI-VOICE-OUT-F01 |
| **今日概览** | 首页概览条 + 待处理单据/库存告警下钻 | `/api/mobile/dashboard` | AI-MOB-HOME-F01 |
| **物料档案** | 搜索 + 多图归档（每物料 ≤5 张） | `/mobile/api/material_archive/*` | AI-MOB-ARCH-F01 |
| **查库存** | 扫码 + 列表双模式，仓库级库存 | `/api/mobile/stock/query` | AI-MOB-STOCK-F01 |
| **离线兜底提示** | `OfflineDataBanner` 缓存回退显式提示 | — | AI-MOB-OFFLINE-HINT-01 |

后端还另有装备未在 App 侧消费：**补货 Agent、仓库巡检、采购/销售跟进工作台、库龄/周转/短缺分析、供应商评估、需求预测、智能库位**（`app/ai/agents/`、`app/ai/analysis/`）。

> **关键发现：后端这些分析能力目前只在 Web 端暴露，App 一条都没接。** 这是最大的一块"已有智能闲置"。

## 二、核心诊断：四个真实缺口

### 缺口 1｜智能"有"，但作业员"摸不到"——离线即瘫痪

这是最严重的问题。当前 App 的离线能力**只有提示，没有降级**：

- Room 库里只有 `materials` 与 `operation_logs` 两张表（`AppDatabase.kt`，`version = 1`）。
- 全仓库 `grep ConnectivityManager|NetworkCallback|isOnline` **零命中** —— 没有任何网络状态监听。
- `OperationLogEntity` 只是**事后日志**（operationType / orderNo / materialCode / quantity / timestamp），**不是待提交队列**，恢复网络后不会自动补传。

实际后果：仓库地下室/货架深处信号差时，作业员扫码入库到一半断网 → 提交失败 → 这一单白扫，必须回到有信号处重来。**这是手机 WMS 最劝退的体验，也是智能化最该先解决的地方。**

### 缺口 2｜后端分析能力与 App 完全断层

后端已有 6 个分析模块、5 个 Agent，App 端**一个入口都没有**。作业员想知道"这个物料还能撑几天""哪些货压了 90 天""这供应商靠谱吗"，必须回办公室开电脑。

### 缺口 3｜作业流程仍是"人找信息"，不是"信息找人"

- 扫码后只显示物料基本信息，**没有"上次领了多少""通常领多少""这个工位常用什么"**。
- 首页概览是**静态汇总数字**（今日入库单数/数量…），不是"你该干什么"的行动建议。
- 没有**异常主动提醒**：某物料库存低于安全线、某单子卡在待确认超 24 小时，App 不会主动说。

### 缺口 4｜语音只覆盖"导航 + 领料建单"，没覆盖高频其他单据

`VoiceCommandViewModel.parseCommand` 的分支只到 `CreateOutboundDraft` + `Navigate/GoBack/GoHome/Logout`。**入库、盘点、查库存、调拨的语音建单全都没有**（`detectOutboundDraft` 是硬编码出库语义）。

## 三、智能化路线图（按投入产出比排序）

### 第一梯队：立刻做，收益最大（P0）

#### ① 离线优先作业队列（Offline-First）

**这是手机 App 智能化的地基，不做这个其余都是空中楼阁。**

| 改动点 | 具体做法 |
|---|---|
| Room 扩表 | 新增 `PendingOperationEntity`（含请求体 JSON、`request_id` 幂等键、重试次数、状态），`AppDatabase.version` 1→2，迁移登记进 `DatabaseMigrations.ALL` |
| 网络监听 | `ConnectivityManager.registerDefaultNetworkCallback`，状态变化即触发队列刷新 |
| 提交改造 | `WmsRepository.submitInbound/Outbound/Stocktake` 失败时**落本地队列**而非直接报错，UI 显示"已暂存，联网后自动提交" |
| 自动补传 | 恢复网络后按序重放，复用后端既有幂等机制（`AIRequestIdempotency`/`request_id`），断网重连、重复点击、并发重放都不会产生重复单据 |
| 离线字典 | 启动时全量拉物料字典进 Room，断网也能扫码识别、本地校验 |

> **必须遵守**：队列只承载"**已由人工确认过**的提交动作"，绝不能让 AI 草稿绕过人工确认直接进队列（AGENTS.md §一 / R5）。补传失败必须**显式告警**，禁止静默丢弃。

#### ② 扫码即知：上下文智能面板

扫码识别物料后，不再只显示名称/规格/库存，而是聚合出一个**"这个物料在此场景下你需要知道的"**信息卡：

- 该物料在**当前仓库**的库存、本库位库存（走 `get_warehouse_stock_quantities`，**严禁裸用 `material.stock`** —— A11/R2）
- **上次入库/出库数量与时间**
- **近 30 天平均领用量** → 直接给出"通常领 N 个"的默认值预填
- 该物料库存告警状态（低于安全线时红字提示）
- 关联供应商、最近采购价

数据源全部复用后端已有能力（`app/ai/analysis/`），只需新增一个聚合的移动端端点。**这一条改动小、体感提升极大。**

#### ③ 首页从"数字看板"变"行动清单"

把 `/api/mobile/dashboard` 从纯统计扩展为**带优先级排序的待办**：

- "3 个物料低于安全库存，点击补货"（接 `analysis/shortage.py`）
- "2 张入库单待确认超 24 小时"（接待确认流）
- "AX-1200 轴承已 90 天无出库，考虑处理"（接 `analysis/stagnant.py`）
- 长按可直接对建议项**生成草稿**（人工再确认后提交）

### 第二梯队：体验跃升（P1）

#### ④ 语音建单扩展到全单据类型

把 `detectOutboundDraft` 的硬编码出库语义抽象为**通用的"建单意图识别"**：

```
「入 6204轴承 100套」     → 生成采购入库草稿
「盘一下 A 区货架」        → 打开盘点并定位 A 区
「查 8*25螺丝 还有多少」   → 直接念出库存数字（纯查询，无需确认）
「把 M8螺母 从 A仓 调到 B仓」→ 生成调拨草稿
```

后端 `voice_out_draft` 的三层容错解析（同音纠正 → 中文数字 → 分隔符归一）与六层降级匹配**已是通用引擎**，扩展成本主要在协议泛化与 App 侧意图路由。**语音播报查询结果**是新增价值点——作业员双手拿货时最需要。

#### ⑤ 图片识别前置质量门禁

当前是"拍完才告诉你不清楚"。改为**拍照取景框实时检测**：清晰度不足/光线过暗/角度太偏时，拍照按钮变灰并给出中文提示（"请靠近一点""光线太暗，请到亮处"）。后端 `documents/image_preprocessing.py` 已有检测逻辑，下沉到端侧或取景帧预检均可。

这一条**直接降低 OCR 返工率**，也是 R5"低置信度回退人工"的前置保障。

#### ⑥ 盘点智能辅助

- **动态推荐盘点范围**：基于历史差异率，提示"B 区上次差异 3%，建议本次重点盘" 。
- **盘点差异实时提示**：扫到的数量与账面差异超阈值时立即黄色高亮（而非等提交后才发现）。
- 补完台账中 `AI-MOB-CHECK-F01`（手机盘点与 Web 盘点单据流对齐）与 `AI-MOB-RPT-F01`（只读报表入口）—— **这两个是台账里仅剩的 3 个"待开发"任务中的 2 个**，且已有明确依赖链，是最顺理成章的下一步。

### 第三梯队：进阶能力（P2）

| 能力 | 说明 | 前置条件 |
|---|---|---|
| **拍照即建全档** | 识别新物料时一次拍全（外包装+标签+铭牌），自动提取编码/名称/规格/单位/图号并归档 | 需 `AI-R07` 物料治理按真实数据调优 |
| **预测式补货建议** | 把 `analysis/turnover.py` + `available_days.py` 推给 App，给出"建议补货点" | 需真实消耗数据积累 |
| **多人协同提示** | "张三正在盘 B 区"避免重复劳动 | 需后端加作业占用状态 |
| **AR 辅助找货** | 摄像头叠加指引到目标库位 | 成本高、收益待验证，暂不建议 |

## 四、必须守住的边界（AGENTS.md 强约束）

做智能化时**任何一条都不能破**，这是这个仓库反复踩坑总结出来的：

| 规则 | 在 App 智能化中的具体含义 |
|---|---|
| **业务铁律** | App 只创建/查看草稿；**提交、审核、完成、作废、删除一律人工**。离线队列补传的必须是"人工已点击提交"的动作 |
| **仓库必填** | 所有出入库/盘点 API 与表单，仓库（及启用库位管理时的库位）必填。App 侧 `WarehouseSelector` 默认选中默认仓，断网时**不得回退到"全部仓库"口径** |
| **R1 分页** | 库存查询/单据列表**禁止依赖默认 page_size 当全量**。要么显式传大 page_size 并按 `total_pages` 翻页合并；要么注释明确"仅取前 N 条"。新增接口必须返回 `total/page/page_size/total_pages` |
| **R2 多仓库** | 涉及库存数量/单据/报表的改动，必须同时验证：①多仓互不串仓 ②历史空 warehouse 脏数据不误判"库存不足" ③汇总=明细全集之和 |
| **A11 库存口径** | 新增代码**禁止裸用 `material.stock`** 做校验，必须用 `get_warehouse_stock_quantities()` |
| **R3 模板重启** | 若改动 `app/templates/*.html`，commit message 与台账**必须注明"生产需重启生效"** |
| **R5 AI 边界** | 低置信度必须回退人工；AI 结果不经确认禁止写入业务数据；不确定时必须明说"我不确定"，**禁止编造** |
| **R6 查重** | 登记新 BUG 前 grep 台账查同根因历史；判为复发的必须**排查所有同类消费点** |

## 五、建议的落地顺序

结合台账"仅剩 3 个待开发任务"的现实，建议这个次序（每个 atomic action 独立 commit + 经 API 通道 push 到 `main`）：

```
① AI-MOB-OFFLINE-01   离线优先作业队列          ← 最高价值，独立可做
② AI-MOB-DASH-F01     首页行动清单化
③ AI-MOB-SCAN-CTX-01  扫码上下文智能面板        ← 体感最强，改动最小
④ AI-MOB-CHECK-F01    手机盘点与 Web 流对齐      ← 台账待开发任务，补齐即闭环
⑤ AI-MOB-RPT-F01      手机只读报表入口          ← 台账待开发任务
⑥ AI-MOB-EMPTY-F01    统一空状态+新手引导       ← 台账待开发任务
⑦ AI-MOB-VOICE-F02    语音建单全单据泛化
```

**先做 ①③**：① 解决"能不能用"，③ 解决"好不好用"，且都不依赖台账里其他任务的解锁关系，可立即开工。

---

## 六、一句话总结

这个 App 的智能化问题**不是"缺 AI"，而是"已有 AI 送不到手上、断网就瘫痪、后端分析能力一条没接"**。

真正的智能化应该让作业员感觉：**掏出手机就知道该干什么、扫一下就知道该领多少、断网了活照干、张嘴说一句草稿就出来了** —— 而不是再多加一个大模型。
