## 二、P0 待修（第一批，建议一周内完成）

### P0-1　已扫的行无法整行删除

| 项 | 内容 |
|---|---|
| **证据** | `ui/screens/ScanScreenBase.kt:662` 仅有「减1」步进；扫码页无删除入口。全仓仅期初库存页 `ui/screens/OpeningStockScreen.kt:253` 有 `removeLine` |
| **现场后果** | 扫错物料编码后，只能反复点「减1」减到 0，或退出重开单据。电气元件编码相近（如仅后缀不同），扫错属高频事件 |
| **建议方案** | 每行增加「左滑删除」或行尾删除图标；删除前二次确认（显示物料编码+名称+数量）；保留「减1/加1」快捷步进 |
| **验收标准** | ① 任意已扫行可一键整行删除；② 删除后计数与合计同步刷新；③ 全部删空后提交按钮置灰（与现有 `enabled = scanLines.isNotEmpty()` 逻辑一致） |

### P0-2　重复扫码静默累加，无任何提示

| 项 | 内容 |
|---|---|
| **证据** | `ui/viewmodel/scan/ScanViewModel.kt:218-221`：同物料+同库位命中即 `existing.copy(quantity = existing.quantity + line.quantity)`，无 Toast、无高亮、无计数动画 |
| **现场后果** | 同一箱货扫两次 → 数量翻倍且无人察觉 → 直接进库存账。**这是账实不符的典型来源**，且事后极难追溯 |
| **建议方案** | 累加时给明确反馈：该行背景色短暂高亮 + Toast「XX 已累计 N」+（可选）轻震动区分"新增"与"累加"两种反馈；连续扫描节流窗口内可考虑提示"重复扫描已忽略" |
| **验收标准** | ① 重复扫同一码，用户能在 1 秒内察觉（视觉或听觉）；② 累加结果正确且行内显示累计数量；③ 不会因提示打断连续扫描节奏 |

### P0-3　扫码成功/失败无声音、无震动反馈

| 项 | 内容 |
|---|---|
| **证据** | 全 `ui/` 目录 grep `vibrat / sound / beep / MediaPlayer` **零命中** |
| **现场后果** | 车间嘈杂、戴手套、强光下看不清屏幕，作业员必须低头确认"扫上没有" → 慢、易漏扫、易重复扫 |
| **建议方案** | 三种状态三套反馈：**成功=短促"滴"+轻震动；未识别/无此物料=低沉双响+长震动；累加=双短响**。设置页提供开关（静音车间/夜班可关） |
| **验收标准** | ① 三种状态反馈可区分；② 可在设置中关闭；③ 连续扫描时不因震动/声音卡顿（`ScannerDialog.kt` 节流窗口需一并验证） |

## 三、P1 待修（第二批，2–4 周）

### P1-1　出库"库存充足/不足"用总账口径，且不拦截超发

| 项 | 内容 |
|---|---|
| **证据** | `ui/screens/ScanScreens.kt:913`：`if ((material.stock ?: 0.0) > (material.minStock ?: 0.0)) "库存充足" else "库存不足"` —— 用的是**全仓库总账** |
| **现场后果** | 与后端当日修复的 11 条 BUG **同一根因**（总账 vs 仓库级）：本仓没货但总账有数 → 显示"充足" → 发不出货或产生负库存；且该判断只是标签，**不拦截提交** |
| **建议方案** | ①手机端展示与校验统一走仓库级可用量；②出库提交前做超发预检并**明确拦截**，给出"本仓可用 N，本次 M"的中文提示 |
| **验收标准** | ① 两个仓库间不串仓（A 仓无货时手机端显示无货）；② 超发被拦截且提示含具体可用量；③ 与网页端口径一致 |
| **联动提醒** | 该项必须与网页端同批收口，只修一端仍会超发 |

### P1-2　无单位换算入口

| 项 | 内容 |
|---|---|
| **证据** | 手机端 `ScanScreens.kt` 无单位相关控件（`unit` 命中仅为 `dp/sp` 布局导入）；后端 AI-R07 已建换算因子（箱/包/盒/打/捆等） |
| **现场后果** | 来料按"箱"、系统按"个"，现场心算 → 数量录错；低压成套场景的螺丝、端子、线号管等小件常按包/箱来料 |
| **建议方案** | 扫码行增加单位下拉，选中后按换算因子折算为基本单位，并回显换算依据（如"1 箱 = 100 个"） |
| **验收标准** | ① 可按来料单位录入；② 折算结果正确且可见依据；③ 与网页端、后端换算因子一致 |

### P1-3　不能拍照上传

| 项 | 内容 |
|---|---|
| **证据** | 手机端 `ScanScreens.kt` grep `camera/image/photo` 零命中；后端已存在 `material_image` 表 |
| **现场后果** | 来料破损、标签不清、数量异议无现场取证，事后只能翻微信照片，与单据对不上 |
| **建议方案** | 单据行支持拍照（可选：来料异常、标签不清、破损取证），图片随单据上传并可在详情页查看 |
| **验收标准** | ① 现场可拍照并关联到单据；② 弱网下先本地保存、联网补传；③ 图片可压缩（考虑 2GB 服务器内存，建议限制分辨率与张数） |

### P1-4　扫码页不能选择库位

| 项 | 内容 |
|---|---|
| **证据** | `ScanScreens.kt` 中库位仅出现在盘点库区字段（`:1565`、`:1578` `stocktakeArea`）与查询页库位分布展示（`:978-988`）；入库/出库扫码时无库位选择 |
| **现场后果** | 若开启库位管理，手机端入库落不到具体货位 → 库位数据是空的，"货在哪个货位"仍然靠人记 |
| **建议方案** | 开启库位管理时，扫码行增加库位选择（默认带出该物料上次库位或默认库位），支持扫码库位标签 |
| **验收标准** | ① 开启库位管理后可指定库位；② 有默认库位时自动带出；③ 库位为空时拒绝提交并给中文提示 |

## 七、推进建议（试行期别贪多）

1. **第一批只做 P0 三项**（3–5 人天），让现场先"用得顺"，同时收集真实使用数据建立上表基线。
2. **第二批做 P1**，其中 **P1-1 必须与网页端同批收口**（同根因，只修一端无效）。
3. **每批上线后做一次 5–10 个 SKU 的抽盘**，验证库存口径是否真的收敛。
4. 大规模推广前建议做一次完整 POC：模拟断网、连续扫码 100 行、多仓交叉出库三个场景。
