## 1. 审计目标

禁止凭印象、禁止"我觉得"。读不到/没法验证的，明确写"未验证"。

## 2. 工具约束（重要，别浪费时间）
本会话**无法执行任何外部进程**：`pwsh` 退出码 3221225794(0xC0000142)、python/git 通过 child_process 抛 EPERM、`stdio:'ignore'` 也是 DLL 初始化失败。
=> **不要尝试跑 pytest / python / git / 任何 .bat**。你的能力是：`glob`、`grep`、`read`、`run_code` 里的 Node `fs`（只能读写文件、统计行数、正则扫描）。
=> 因此所有结论都是**静态分析**结论；涉及"运行时才能确认"的要标注 `[需运行验证]`。

## 4. 分级标准
- **P0 致命**：数据错误/账实不符/资金损失/越权或未授权访问/注入/敏感信息泄露/生产不可用。
- **P1 严重**：明确功能缺陷、边界条件触发错误结果、并发/事务缺陷、性能悬崖、错误处理缺失导致脏数据。
- **P2 一般**：可维护性硬伤、违反仓库规则（A1–A14 / R1–R8）、性能隐患、体验缺陷、测试缺口。
- **P3 轻微**：代码异味、重复、命名、文档漂移。
每条必须标注「确认程度」：`已确认`（读代码可断定）/ `高度可疑`（需运行验证）/ `风险提示`。

## 5. 单条 findings 格式（严格遵守）

```
### [P1] 标题（≤40字）
- 位置：`app/routes/in_order.py:1234-1245`（可多行）
- 现象：一句话说清"发生了什么错"
- 证据：贴 3-10 行关键代码/查抄关键 SQL/字段
- 影响：谁能触发、会造成什么业务后果（账/钱/权限/数据）
- 根因：为什么错（缺校验/口径不一致/漏事务/绕过统一层…）
- 建议：最小可执行修复（具体到函数/校验/索引）
- 确认程度：已确认 / 高度可疑 / 风险提示
- 关联规则：A11 / R2 / §二 …（若有）
```

按 P0→P3 排序。**同一根因的多个消费点合并为一条，并列出全部点位**（仓库规则 R6 要求排查所有同类点）。
