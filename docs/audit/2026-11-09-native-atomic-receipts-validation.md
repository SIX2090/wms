## 根因与范围

原 mobile_api_idempotent 在业务提交成功之后另行保存回执。回执写入失败会留下已执行的业务；响应在提交后丢失、客户端重试时可能再次执行。同一请求号换内容也会直接重放旧响应，期初行编辑没有绑定路径里的行 ID。请求号使用 or '' 还会把 0、False、空列表当成无请求号。

本阶段复用既有 MobileApiRequest 表与 stage_document_response，不新增 schema 或生产迁移：

| 接口 | 本阶段行为 |
| --- | --- |
| POST /api/inbound | 业务、库存与成功响应在同一事务提交 |
| POST /api/outbound | 保留并复用回执已取得的写事务，不为取写锁回滚占用记录 |
| POST /api/stocktake | 保留批次锁、实盘归属与只生成调整草稿的既有边界 |
| POST /api/opening_stock | 期初建账及回执原子提交 |
| POST /api/opening_stock/<line_id> | 保留原签名版本及写锁，回执绑定具体行路径 |
| POST /api/mobile/inbound_draft | 草稿、可选自动建物料及回执同事务，仍不完成单据或修改库存 |

新回执按账号、endpoint、请求号隔离，并绑定内容、路径、方法与查询参数；同号不同内容返回 409。已有原生回执保留原响应，不猜测其缺失的历史请求内容；无请求号旧客户端保持原路径，不能据此承诺无键重试也能去重。九个原生装饰器消费点一起修正非字符串请求号校验；其余语音／AI 业务链仍需进一步核查，不宣称全部移动端幂等完成。

原生提交必须先暂存成功响应才能提交，避免未来遗漏 stage 时只保存业务。监听器作用于当前请求的 Session，返回时移除；释放 SAVEPOINT 不当作外层事务已成功。已确定提交成功后的异常可以返回同一已暂存响应；底层 DBAPI 实际提交却抛出异常时首次返回失败，重试仍从同事务内已保存回执恢复原单据，不重复业务写入。
