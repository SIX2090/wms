## 一、库存正确性（最关键维度）—— 🟢 B+

这是本系统**最扎实、最值得称道**的部分。核心是三账体系（`INVENTORY_TRUTH.md`）：

```
③ 流水账 stock_transaction（append-only，事实来源）
        ↓ 按 warehouse_id 归属累加
② 库位账 location_inventory（开启库位管理时的仓库级真相）
        ↓ 跨仓库跨库位累加
① 总账 material.stock（全局合计）
```

### 1.1 设计上的优点（站在专家视角的高度评价）

1. **恒等式与派生方向被固化为文档**：`① = Σ② = Σ③`，且只允许 `③→②→①` 单向派生，禁止从全局倒推仓库级。这在 90% 的 WMS 里是散落在代码注释里的隐性约定，本项目把它升格为权威文档 + 自动化判据（`verify_inventory_identity.py`），是**罕见的工程成熟度**。

2. **仓库级口径已收口**：A11 lint 规则禁止业务代码裸用 `material.stock`（全局总账）做校验，强制用 `get_warehouse_stock_quantities()`。这直接掐断了历史上"多仓串仓"这一根因在 20+ 个消费点反复复发的根源。

3. **三账写入已收敛到统一入口**（`warehouse_stock_service.py` 的 `apply_stock_delta` / `apply_transfer_pair` / `apply_opening_balance`），批 1–5 已完成，只剩 `requisition.py` 扣减侧（批 6）因语义变更风险单列。

4. **"归属不猜"原则**：无法唯一确定的流水 `warehouse_id` 保留 NULL，宁可"看得见的空洞"也不伪造归属。这是防范账实分裂最正确的哲学。

### 1.2 遗留的结构性风险

| 风险 | 说明 | 等级 |
|---|---|---|
| **并发扣减非原子（TOCTOU）** | 仓库级可用量是"读"出来的，条件 UPDATE 只看全局 `stock>=qty`；手机扫码/Android 出库路径无 `_acquire_order_write_lock`，并发下同仓同物料可超扣 | 🔴 高危（单人使用暂不触发，但架构隐患存在） |
| **库位管理开启即事故** | `location_inventory` 全表仅 2 行且为脏数据；一旦有人在设置里开启"库位管理"，1243 个物料库位账恒为 0，所有出库被拒 | 🔴 高危（当前开关为关，属"未来防御"） |
| **`revert_in_order` 流水归属修正疑似死代码** | 写入在加锁前，而 `_acquire_order_write_lock` 第一步即 rollback | 🟡 中 |

> 单人使用场景下，并发风险不会实际触发，但这是"环境画像"（AGENTS.md §〇）明示的假设——一旦转为多人使用，这些隐患会立即升级为 P0。

## 二、规则与工程治理 —— 🟢 A-

这是整套系统**最突出的资产**，同样规模的项目里我很少见到这么完整的治理体系：

1. **22 条防 BUG 规则**（A1–A14 + R1–R8），每条都对应历史上真实踩过的坑，且有 lint 机械化防护（`lint_wms_rules.py`）。
2. **BUG 台账闭环**：435 个去重 BUG ID，分片登记 + 索引 + `query_ledger.py` 查询，修复必须含"生效确认"（A13 门禁）。
3. **三级门禁**：pre-commit 钩子 → CI 三工作流 → 推送后同步校验（`verify_remote_sync.py`）。
4. **反复 BUG 模式清单（R 系列）**：锁×17、多仓库×11、分页×11 等根因被显式归类，R6 要求"同根因必须排查所有消费点"。

**唯一的问题**：这套体系**依赖人工/AI 自觉执行**，而当前 CI 红灯（P0-1）恰恰说明——规则写得再好，门禁本身失效时，整个治理链条就断了。这正是 AGENTS.md §三"CI 全绿是硬性前置条件"的用意所在。

**CI 红灯根因**：`Security scan - pip-audit` 阻塞门禁失败。经本次复核查证：

- 这是 **10-20 报告之后新出现的问题**（10-20 报告记录 CI #1650 为 success）

**这是当前最需要立即处理的事项**，因为：

## 八、15 年专家视角的优先级建议

按"先止血、再加固、后还债"排序：

### 第一优先（止血，本周内）
1. **修绿 CI**：升级 Pillow 等有 CVE 的依赖到安全版本，重跑 pip-audit，恢复全绿门禁。
2. **确认 A04/A05 整改是否已合并并生效**：扫码写接口 CSRF、API 登录限流——这两项是公网可达系统最实在的安全缺口。

### 第二优先（加固，本月内）
3. **做一次真实的备份恢复演练**：删一个测试库 → 从备份恢复 → 校验账实一致。把"备份可恢复"从纸面变成实证。
4. **库位管理开关加前置校验**：开启前先跑库存恒等式，有差异则拒绝开启，防止"一键开启即事故"。

### 第三优先（还债，季度内）
5. **app.py 存量路由分阶段迁移**：制定分阶段计划，每次迁移一批 + 全量回归，不搞一次性大重构。
6. **并发扣减原子化**：把仓库级校验下推为同一条 SQL（`HAVING SUM(quantity) >= :qty`），为未来可能的多人使用做准备。
