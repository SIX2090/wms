# WMS 全系统流程关联逻辑审查

日期：2026-10-14。依据：`docs/workflows/WMS_FLOW_ATLAS.md`、30 章图册及当前代码 `06736aaf`（业务代码基线 `21b97ce2`）。

## 结论与范围

**主干设计基本成立，但不能认定所有跨流程逻辑正确。** 本次确认 4 类程序问题，涉及 7 个隔离数据库复现场景；另有 4 处图册表达需要澄清。问题集中在来源数量、退货依赖、单位维度及完成时的仓库有效性。普通单据“草稿不动库存，完成记账”的设计本身没有因此被否定。

本次只分析、保存证据，不修改业务代码，不操作生产单据。复现脚本强制使用内存 SQLite，创建的是测试用户、测试仓库和测试物料。既有受影响模块 87 项测试全部通过，但这些测试未覆盖下面的边界，不能以测试全绿证明业务关联完全正确。

当前单人使用、4 仓库、未开启库位。已接受的入出库无作废态、主链路无独立审核岗，不作为缺陷。

## 实测确认的程序问题

### S1 / 高优先级：同一来源行拆成多行，可突破数量上限

来源行数量 10，目标单中同一来源行填两行，各 6。逐行校验均满足 6 ≤ 10，但整单实际数量 12 > 10，保存和完成都成功。

| 场景 | 初始与前置库存 | 完成结果 | 应有规则 |
|---|---|---|---|
| 销售订单下销售出库 | 初始 100 | 库存 88，出库 12 | 当前单按来源行汇总后不得超过可出库量 10 |
| 销售退货 | 初始 100，先出库 10，剩 90 | 库存 102，退回 12 | 完成退货累计不得超过已完成发货量 10 |
| 采购退货 | 初始 100，先入库 10，变 110 | 库存 98，退走 12 | 完成退货累计不得超过来源已完成入库量 10 |

根因：`app/app.py` 的 `sales_outbound_remaining_check`（35215）、`sales_return_remaining_check`（35300）、`purchase_return_remaining_check`（35387）按当前明细逐行比较，未先合计当前单重复来源行。销售出库、两种退货共享这种缺口。

建议：按**来源明细 ID**汇总当前单数量，结合其他有效单据占用/完成量计算剩余，再一次比较；保存、单张完成、批量完成沿用同一口径，完成时加锁重查。不能简单禁止“同物料出现多行”，不同来源行、合同或项目分行本来可以合法。

### S2 / 高优先级：完成退货后，原出入库仍能反提交

| 场景 | 实测链路 | 最终异常 |
|---|---|---|
| 销售 | 100 → 出库 10 为 90 → 退货 4 为 94 → 原出库反提交 | 库存 104；原单 pending，发货累计 0；退货仍 completed |
| 采购 | 100 → 入库 10 为 110 → 退货 4 为 106 → 原入库反提交 | 库存 96；原单 pending；采购退货仍 completed |

问题不是“反向流水算错”，而是已完成退货失去合法的来源履约事实。流水、余额可以仍然数值一致，所以三账一致检查不能替代业务依赖检查。

依据：`app/routes/out_order.py:1209` 的 `revert_out_order` 回冲并更新销售发货进度；`app/routes/in_order.py:2399` 的 `revert_in_order` 检查下推关系，但 `app/app.py:25779` 的 `_source_has_active_push` 仅覆盖 `DocumentPushLine`，不等于直接退货来源外键依赖。

建议：反提交前检查**回退后的有效来源数量**仍能覆盖完成退货量。销售订单可能有多张发货单，不宜一看到退货就禁止所有发货单回退，应逐来源行核算剩余有效发货 ≥ 完成退货。采购原入库整单回退应检查其来源明细被哪些完成退货引用。不能只看来源表头，避免漏掉跨单明细关联。需要处理退货时，由人工先反提交退货，再处理原单，禁止自动级联撤销。

### S3 / 高优先级：BOM 单位与库存单位不同，直接按数值扣库

物料库存单位“个”、库存 100；BOM 明细填写 2“箱”。保存 BOM、生成领料单、完成领料均成功，库存变成 98“个”。这相当于计算 `100 个 − 2 箱`，单位维度不成立。

没有定义换算关系时，不能推定一箱是多少个，也不能把箱当个。`app/models/master_data.py:49` 的 Unit 没有换算系数；`app/routes/bom.py:69` 的 `_prepare_bom_items` 校验单位存在，生成领料时带入该单位；`app/routes/requisition.py:558` 的完成逻辑直接使用数量扣库，不进行换算。

建议：短期统一 BOM/领料数量使用物料库存单位，覆盖表格保存、导入、旧入口、生成和编辑领料单；长期若需要多单位，先明确基本单位、换算系数、精度和历史数据处理，再实施。前一轮 BOM 检查验证了单位字段保存，漏验了它与库存扣减的衔接，本次已补实测。历史台账 `BUG-2026-08-16-021` 已提及单位换算能力缺失，本报告进一步证实了混合单位进入实际扣库链路的后果。

### S4 / 中优先级：工单领料完成时未重新检查仓库停用

在有效仓库生成 BOM 领料草稿，然后停用该仓库。完成仍返回成功，库存从 100 降为 98。有效性应在最终记账时复核，不能只靠录单时的选择框。

依据：`app/routes/requisition.py:558` 检查仓库非空，但没有重新验证仓库 active；`app/app.py:4756` 的 `deduct_stock_atomic` 查仓库库存，不替代 active 校验。

建议：最终完成入口统一复核仓库有效性，含批量入口。静态检查还发现 PC 盘点完成、调整完成没有直接调用同类 active 校验，列为同根因排查候选；**这两处尚未做动态复现，不将它们宣称为确认漏洞**。委外订单表头“完结”不直接写库存，不能仅因它没有仓库 active 校验就判为库存缺陷。

## 跨流程关系与正确口径

| 关联 | 应如何理解 | 本次判断 |
|---|---|---|
| 采购申请 → 采购订单 | 审批通过允许下推；申请人工完成不强制已有订单 | 主流程表达需澄清，非强制串行 |
| 采购订单 → 采购入库 | 草稿占用收货额度与完成收货事实分开；反提交后草稿占用不等于释放 | 设计可成立；不要只看一个 received 数字判断实收 |
| 手工采购入库 | 可无采购订单，关联订单只是可选来源 | 正确，不应改成强制关联 |
| 销售订单 → 销售出库 | 订单确认不扣库存；草稿占额度，完成扣库并跟踪履约 | 主干正确，重复来源行缺口见 S1 |
| 销售出库 → 销售退货 | 退货依据已完成发货，完成增加库存 | S1 数量上限、S2 反提交依赖存在缺口 |
| 采购入库 → 采购退货 | 退货依据已完成入库，完成扣库存 | S1 数量上限、S2 反提交依赖存在缺口 |
| 来源下推 → 目标反提交/删除 | 下推占用可能随目标草稿继续保留；反提交并不必然释放，删除才释放相关记录 | 必须区分占用关系与完成事实，不能把反提交画成所有引用自动解除 |
| BOM → 工单领料 | BOM 是用量模板，生成草稿不扣库存；领料完成才扣库 | S3 单位口径、S4 仓库有效性需修 |
| 领料 → 成品入库 | 两项独立库存动作，当前不等于完整生产计划和工序闭环 | 不能将领料完成解释为自动产生/完成成品入库 |
| 调拨 | 源仓减、目标仓加；反提交须目标仓具备可回退量 | 配对设计正确，物料全仓合计不变 |
| PC/扫码盘点 → 调整 | 盘点先记录实盘与差异，调整草稿另行人工完成才改变库存 | 主干正确；无差异分支应更清楚 |
| 扫码记录作废/盘点反提交 | 已有完成调整时不能直接撤销上游盘点事实 | 已有相应阻断，不能画成自由撤销 |
| 委外订单 → 发料/收料 | 表头状态和子单库存事实分别维护 | “订单完结”不能直接作为所有明细履约数量充分的证明 |
| 期初库存 → 余额 | active 期初保存按增量记账，删除回冲 | 不套用普通单据草稿/完成两阶段 |
| 手机录单 → 完成 | 批量草稿有两阶段；部分旧快捷入口直接完成 | 图册已分别展示，应按入口辨认，不能泛化所有手机保存都不扣库 |
| 库存 → 报表/打印/分享 | 报表读事实；打印与分享状态独立于业务完成 | 状态分离正确，打印失败不应回退库存 |
| AI/OCR → 单据 | 辅助识别/建议与草稿确认，不取代人工高风险动作 | 图册边界合理，本次未对所有 AI 工具进行动态授权测试 |
| 备份 → 恢复/升级 | 备份是运维链路，不是业务状态；恢复须停机处理 | 默认自动备份 02:00、保留 30 天，清理范围为自动日备份；配置可改变，不能把默认当固定常量 |

## 图册表达需要澄清的 4 处

1. **05 采购申请**：主链把创建采购订单放在申请完成前。`complete_purchase_request`（`app/routes/purchase_request.py:687`）要求申请已 approved，并不要求已下推采购订单。图应把下推订单、人工完成画成审批后的独立分支。
2. **12 BOM 领料**：手工新增工单领料的分支从“已生成 BOM 草稿”处引出，容易理解成必须先生成 BOM。手工录入应作为独立入口，直接汇入草稿编辑节点。
3. **14 PC 盘点**：先画“生成差异调整草稿”再旁挂“无差异不生成”，顺序不清。应先判断是否有差异，有则生成并人工完成调整，无则结束盘点。代码本身有无差异分支。
4. **19 三账校验**：必须区分业务校验失败回滚与可配置的三账监测。`app/services/warehouse_stock_service.py` 的 guard 有启用和 strict 开关，普通告警模式不必然抛错回滚；不能看图就认为生产每次写库都强制三账一致才提交。这是图册准确性问题，本报告不改变配置策略。

总览图已注明模块不是必须依次执行；第 04 章的“检查下游”是应有共同骨架，S2 表明实际部分退货关联尚未完整实现，不能以图上有该节点作为实现证据。

## 验证证据与后续顺序

复现证据：[`WMS_FLOW_LOGIC_PROOF_20261014.json`](WMS_FLOW_LOGIC_PROOF_20261014.json)，7 场景；脚本：[`flow_logic_reproduce.py`](flow_logic_reproduce.py)。脚本运行前即覆盖数据库 URL，初始化后再次断言内存 URL；严禁移除隔离保护后运行。

既有回归命令：

```powershell
python -m pytest tests/test_bom_lifecycle_audit.py tests/test_requisition_bom_picker.py tests/test_purchase_return_e2e_p0.py tests/test_sales_audit_006_complete_remaining_check.py tests/test_sales_audit_008_warehouse_active_recheck.py tests/test_p1_7_three_ledgers_business_paths.py tests/test_inv_revert_001_check_scan_void.py tests/test_bug_2026_09_06_001_check_uncounted_guard.py tests/test_bug_2026_09_06_002_check_period_movement.py -q
```

结果：87 passed，156 warnings。动态复现采用关闭三账附加断言的隔离配置；该配置不改变生产设置，也不取消来源数量、状态、单位、仓库等业务规则应有的约束。证明的是该配置下公开路由接受了上述非法业务组合，不宣称所有生产配置均已逐一实测。
