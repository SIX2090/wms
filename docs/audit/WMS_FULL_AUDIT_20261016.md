## 已确认问题与处理建议

### A01 / P1：恢复工具不能证明服务已停机

- 位置：[restore_backup.py:39](../../scripts/restore_backup.py#L39)、[覆盖入口:110](../../scripts/restore_backup.py#L110)。
- `_db_locked()`仅尝试`BEGIN IMMEDIATE`。数据库仍被其他连接打开但没有写事务时返回False；与其“Windows独占打开测试”和“WMS在跑直接拒绝”的说明不符。
- 临时SQLite实测：保持连接打开，检测仍返回False。它不能作为随后`shutil.copy2`覆盖主库的停机证明；WAL/SHM也没有统一处理。
- 建议：独立验证本系统进程/服务已停止，检查目标身份，采用明确的离线恢复流程并拒绝不确定状态。验证应包含另一进程持有空闲WAL连接的情况。

### A02 / P1：恢复接受非 WMS SQLite 数据库

- 位置：[restore_backup.py:68](../../scripts/restore_backup.py#L68)、[非WMS分支:133](../../scripts/restore_backup.py#L133)。
- 恢复前只检查SQLite物理完整性，不校验WMS表及必要字段；恢复后发现非WMS结构，仍打印提示并返回0。
- 临时库完整复现：只有`unrelated_data`表的SQLite文件被接受，目标库覆盖后只剩该表，退出码0。没有触碰生产库。
- 建议：覆盖前完成WMS结构/版本和关键表校验；失败不得改变目标文件，并保留恢复前快照。

### A03 / P1：重启可能实际没有替换旧进程

- 位置：[restart.py:62](../../app/restart.py#L62)、[启动与检测:76](../../app/restart.py#L76)。
- 脚本寻找不存在的`app/stop_wms.bat`；仓库实际提供`app/stop_wms_offline.bat`。随后启动子进程，只凭端口登录页200判成功，没有确认新子进程存活或服务版本。
- 临时目录、模拟Popen/HTTP复现：停止函数没有调用，旧服务200即可让main返回0。没有启动/停止真实服务。
- 建议：统一停止入口，核对PID/可执行文件/命令行；等待旧进程退出，再验证新PID、版本及HTTP响应。

### A04 / P1：一键更新网络失败后不会恢复旧服务

- 位置：[update_from_github.bat:157](../../update_from_github.bat#L157)、[fetch失败退出:172](../../update_from_github.bat#L172)。

- 源码控制流确认；未在生产断网运行更新脚本。
- 建议：下载/快进可行性检查尽可能在停机前完成；停机后的每个失败出口都应恢复旧代码、依赖与服务，显示真实结果。
