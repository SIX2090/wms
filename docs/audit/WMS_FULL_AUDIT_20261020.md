## 具体发现

### A01：导入仓库静默错配（P1）

位置：`app/routes/requisition.py:894`、`:896`、`:942`。

`aliases` 没有仓库字段，创建单据固定写入 `warehouse=import_default_warehouse`。隔离夹具配置默认仓 A，Excel 明确填写仓 B，导入返回 HTTP 200，而单据保存为仓 A。若未配置默认仓，还会保存空仓草稿。

影响：四仓场景中导入单据的仓库归属与操作员输入不一致；后续人工完成将按已保存仓库扣账。**本次只复现错误草稿，未在生产完成任何单据。**

建议：解析仓库 ID/名称/编码；显式填写的无效或停用仓应拒绝，缺省时才使用有效默认仓，无默认仓拒绝。同行同单的仓库冲突需明确报错。回归至少覆盖 A/B 隔离、无默认仓、停用仓和同单冲突。

历史关系：10 月 18 日 inventory 分册同根因已提及，但旧描述“全部 NULL”不符合当前代码；本轮纠正为“忽略指定仓、强制默认仓，缺默认值才 NULL”。未重复计算成两个问题。

### A02：表单填写的领料人丢失（P2）

位置：`app/templates/document_table_form.html:183`、`:719`、`:725`；`app/routes/requisition.py:192`。

页面有 `name="picker"` 输入框，但 `collectHeader()` 的 requisition 分支没有收集 `picker`；后端用 `(header.get('picker') or '').strip()` 覆盖该字段。

隔离执行实际 `collectHeader()`，输入“张三”后得到的 payload 不含 picker，随后保存返回 HTTP 200，数据库中的 picker 为 `""`。编辑原有单据走同一路径时，也存在清空已保存领料人的风险。

建议：表单收集并提交 picker，新增从实际 JS payload 到数据库回读的测试。既有 `tests/test_requisition_picker.py:98` 手工构造带 picker 的 JSON，只证明后端接受该字段，不能证明前端会发送它。

### A03：统计导出包含未完成草稿（P2）

位置：`app/routes/report.py:343`、`:373`、`:402`；`app/static/js/app.js` 的 `WMS_REPORT_PRINT_PARAM_MAP`。

旧导出只按仓库与日期查询，没有状态、关键词筛选；别名 `/report/inout/export` 复用相同函数。隔离创建 pending 入库，带 `status=completed` 和不匹配 search 请求导出，生成的“入库统计”仍有该草稿 7 个单位。

影响：纸面/Excel 与屏幕筛选不一致，未实际发生的出入库会出现在统计中。这里复现的是导出内容错误，未证明生产库存账因此变化。

建议：明确这是“已发生统计”还是“单据清单”；前者只计 completed，后者透传筛选并显示状态。统一页面、导出和打印筛选函数，保留全集合计，不能只导出当前分页。

### A04：会话鉴权的扫码写接口绕过 CSRF（P2）

规则：会话凭证的状态变更必须校验 CSRF；Bearer 凭证可以采用独立策略。

位置：`app/app.py:3509` 前缀批量豁免；`app/routes/mobile.py:83` 双通道角色装饰器；`:380` `/mobile/api/scan_submit`。

在隔离环境设置 `WTF_CSRF_ENABLED=True`，仅带已登录会话、不提供 CSRF Token，POST 扫码入库仍返回 HTTP 200，测试库存从 20 变成 22。现有装饰器检查身份和角色，但没有根据会话/Bearer 区分 CSRF。

利用边界：这是服务端校验缺口；当前 `SameSite=Lax` 会缓解普通跨站 POST，探针没有绕过浏览器 SameSite，也没有证明任意外站可直接攻击生产。不能将其报告为“未登录即可改库存”。

建议：复用已经修好的打印队列策略，会话分支强制 CSRF，Bearer 分支验证令牌；取消按 URL 前缀默认豁免。检查 mobile/AI OCR 所有同类双通道消费点。

### A05：API 登录缺少 IP 级失败限流（P2）

位置：`app/routes/native_api.py:901`；对照 `app/routes/user_auth.py:127`。

Web 登录用 `login_fail:{request_ip}` 做窗口限流；原生 API 只针对已存在用户累计失败。隔离同 IP 连续请求 65 个不存在账号，响应全是 401，没有 429。

影响：应用层无法限制跨用户名枚举和密码喷洒，也会产生大量失败登录日志。已有账号锁定仍存在，单人场景和外围网关可降低风险，因此不按已证实账号接管定级。

建议：两套登录共享 IP 失败窗口，未知账号也计入，并覆盖限制解除、代理 IP 信任边界与正常登录。探针不测试任何生产账号或密码。

### A06：改仓库名漏同步单据（P2）

位置：`app/routes/warehouse.py:139`、`:151`；`app/models/documents.py` 的 `InventoryCheck.warehouse`、`AdjustmentOrder.warehouse`。

改名同步清单含入库、出库、委外主单、工单领料、售后、销售和调拨，漏掉盘点单和调整单。隔离改名请求返回 HTTP 200，Warehouse.name 已变为“仓库A新名”，这两类单据仍是“仓库A”。

影响：后续按现名筛选或按旧名解析仓库可能失败。是否已有生产历史受影响需专门按旧名核对，不能仅凭此复现断言生产单据丢失。仓库编码变更、扫码盘点和委外子单也应纳入同根因消费点排查。

建议：短期补齐统一同步入口；长期以稳定 warehouse_id 作关联、名称作展示快照。既有改名测试名称虽为“all documents”，夹具和断言未覆盖盘点/调整，不构成全集覆盖。

### A07：期初库存换库位不迁移账（P2，当前未启用）

位置：`app/routes/opening_stock.py:275`；`app/app.py:8390`、`:8419`、`:8424`。

编辑先把 `opening.location` 改成新库位，库存服务仅在 `quantity_delta != 0` 时执行。隔离开启库位管理，先建 L-A 的 10 个期初，再改成 L-B、数量仍 10，得到期初行 L-B、库位账 L-A=10，没有 L-B 行。

影响：开库位后单据与库位余额分叉，后续回冲可能在错误库位发生。**生产开关仍为 0，本次未更改它，不将此列为当前已发生账错。**

建议：在有事务内回冲旧库位并写新库位的可靠实现前，后端禁止改动已有期初行库位；实现时覆盖数量不变/增加/减少、回冲失败回滚与删除链路。

### A08：AI 外部端点配置为明文 HTTP（P2，部署风险）

位置：生产 `system_setting.ai_llm_base_url`（仅记录 scheme，不输出地址/密钥）；`app/app.py:12971`、`:12981`、`:12994`。

只读配置仍为非回环 HTTP。代码已有告警和可选 `WMS_AI_REQUIRE_HTTPS=1` 硬门禁，请求头使用 Bearer Key。告警只能提示，不能给 HTTP 流量加密。

边界：本轮未发 AI 请求，未读取运行进程环境或证明发生了明文传输；如硬门禁开启，则请求会被拒绝，表现为 AI 功能不可用。旧报告已记录服务端 TLS 尚未就绪，属于未闭环部署项，不能重复声称新发现。

建议：网关提供有效 HTTPS、验证证书后切换配置并开启硬门禁；保持人工录入回退。不能通过关闭证书验证“解决”连接问题。
