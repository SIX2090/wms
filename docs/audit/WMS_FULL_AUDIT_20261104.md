## 四、当前仍存在的风险（按优先级）

### 中风险

1. **app.py 仍为 36,415 行巨石**（94 条存量路由 + 全局拦截器 + 启动迁移）。A10 棘轮只拦新增，存量未拆。任何跨模块改动仍需在大文件内定位，回归半径大。
2. **「修复→生产生效」闭环缺口**：台账中大量条目状态为「已修复（代码及 CI）；生效确认：待确认，生产需重启」。生产部署（Windows 实机重启）与代码交付节奏脱节，存在「代码已绿但现场仍踩坑」的窗口期。
3. **模板内联 JS 治理未完成**：100/142 模板含内联 `<script>`（约 2.7 万行），裸 fetch 扫描对模板仍为 warn 模式，棘轮基线未定（F3.7 观察期）。
4. **4 项未修复 BUG**（台账如实登记）：BUG-2026-10-16-001（离线恢复占用与结构校验，首轮回滚）、BUG-2026-10-16-002（文件维护回落生产库）、BUG-2026-10-25-026（共享盘点混入全局库存口径）、BUG-2026-10-25-027（库位推荐陈旧缓存）。其中 026 属库存口径类，建议优先排批。
5. **两人独立账号新边界**（2026-11-04 用户确认）：IMP-02 已上线同单编辑冲突保护，但权限矩阵、操作归属、库存并发（10-10 审计 1.2 的 TOCTOU 场景）需按「多人」重新评估，现有单人假设已失效。

### 低风险 / 已知取舍

6. 28 个源码字符串测试（主要 Android，本地无 SDK 的既定取舍，CI 为唯一编译证据）。
7. 金额列部分用 Float（10-10 §3.4，未重新核验，属存量）。
8. 云密钥处置需现场执行（仓库不可见）。
9. 沙箱审计环境依赖与钉版存在小差异（SQLAlchemy 2.0.51/2.0.52），不影响静态结论。

## 五、突出优点

- **缺陷治理体系是同类小型项目中的顶级实践**：A1–A14 机械化门禁 + R1–R8 反复模式防护 + 台账「生效确认」闭环 + CI 全绿门禁 + 每日定时探活，且本次实跑全部 0 违规。
- **库存账可信度有判据背书**：三账恒等式校验器、逐仓隔离、37 个写入点正反对称、A11 全量硬门禁 0 违规。
- **安全纵深**：SECRET_KEY 持久化回退链、生产 Cookie 硬门禁（必须显式放行才允许不安全配置）、登录限流、CSRF 全局 + 扫码双通道、CSP/HSTS、文件上传三重校验、日志脱敏。
- **审计发现的高兑现率**：10-10 定级 D 的安全与运维，3.5 周内修复至可核验项全部闭环。
- **文档诚实**：README/台账明确区分「代码已推送 / CI 已验收 / 生产已部署」三种状态，不混报。

## 六、改进建议（不排期，供决策）

1. 继续将 app.py 存量路由与拦截器按域外迁至 `app/routes/`，目标一年内降至 1 万行以内。
2. 为「生产生效确认」建立发布看板：每次生产重启后批量回填台账生效确认，消除待确认积压。
3. 模板内联 JS 分批抽到 `app/static/js/pages/`，F3.7 观察期结束后定棘轮基线转 strict。
4. 按两人账号新边界做一次专项并发/权限审计（重点：10-10 审计 1.2 的仓库级扣减 TOCTOU 是否仍开放）。
5. 优先排批修复 BUG-2026-10-25-026（库存口径类，R2 活跃场景）。
